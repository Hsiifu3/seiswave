# SeisWave UI 设计与验收测试策略调研

> 目标对象：SeisWave（PySide6/Qt6 桌面科学计算 GUI，核心依赖 `numpy` / `matplotlib` / 大量数值计算）
>
> 本报告聚焦两件事：
> 1. 如何把科学计算桌面软件的 UI 做得更现代、可维护、可扩展；
> 2. 如何建立一套适合 SeisWave 的 GUI 验收测试体系，而不是只做单元测试。

---

## 0. 执行摘要

SeisWave 目前已经具备比较清晰的向导式工作流和分栏式参数/结果布局基础：主流程是“规范谱 -> 选波 -> 生成 -> 组合”，人工波生成面板已经采用了“三栏 + 卡片 + 底部状态栏”的结构，这非常接近现代工程软件常见的信息架构。

但从 2024-2025 年工程/科研 GUI 的实践看，SeisWave 下一步应该把重点放在以下四点：

1. **从“样式表美化”升级到“设计系统”**：建立 design tokens（颜色、间距、字号、状态色、圆角、密度）+ 组件层（按钮、参数卡片、图表容器、状态条、表格）+ 页面层（向导步骤、组合结果页），避免零散 QSS 演进成维护负担。
2. **将复杂参数面板做成“渐进披露”**：默认只展示关键参数，把高级参数、诊断参数、算法参数折叠或放入二级区域；不同地震动类型下的动态参数要显隐稳定、标签清楚、默认值可信。
3. **验收测试必须分层**：不要把 GUI 自动化当成唯一真相。对 SeisWave 最可靠的策略是“核心数值黄金样例测试 + GUI 关键流程测试 + 少量端到端视觉回归”。
4. **CI 中优先采用 headless Linux + Xvfb**：对 Qt/PySide6 应用最现实，且与 `pytest-qt`、截图回归、matplotlib `Agg`/`QtAgg` 切换兼容性较好。

如果只给一个结论：

- **UI 方向**：保留当前向导式结构，强化参数卡片系统、状态反馈、图表一致性、可访问性与中英文切换能力。
- **测试方向**：短期用 `pytest` + `pytest-qt` + 黄金数据集；中期补截图回归和 smoke E2E；重度方案再引入 Squish 或商业级 GUI 自动化。

## 1. SeisWave 当前界面基础与约束

## 1.1 已有结构基础

从当前代码和需求文档看，SeisWave 已经具备几个很好的方向：

- 主窗口是**四步向导式流程**：`规范谱 / 导入 -> 选波 -> 人工波生成 -> 组合 / 导出`，符合工程软件“按工作流组织任务”的模式。
- 人工波生成面板使用了**左参数 / 中绘图 / 右摘要**的三栏结构，并通过底部状态栏反馈进度，适合数值计算任务。

- QSS 已经区分了**主色、辅色、警告色、成功色**，说明后续提炼 design tokens 成本不高。
- 需求文档明确提出：macOS 原生支持、深浅色主题、中文界面、GUI 在计算过程中不冻结。

## 1.2 关键产品约束

SeisWave 不是通用办公软件，而是典型的**科学/工程计算桌面应用**，因此 UI 和测试策略必须同时服务于以下特征：

- **高参数密度**：规范谱参数、选波参数、人工波参数、隔震前后周期、迭代控制、导出设置等。
- **高解释责任**：结果不仅要“算出来”，还要让工程师知道“为什么这样算”“误差有多大”“是否满足规范”。
- **图表是主界面，不是装饰**：反应谱、时程曲线、筛选结果、误差趋势必须是一级公民。
- **长耗时计算存在**：需要工作线程、进度反馈、可取消、出错可定位。
- **数值正确性比 UI 像素更重要**：验收测试不能只测按钮能不能点，要测结果是否仍然满足规范与数值容差。

## 2. UI 设计体系：2024-2025 的现代科学计算 GUI 实践

## 2.1 现代趋势：从“单窗体堆控件”转向“任务驱动工作台”

2024-2025 年的工程软件和科研工具，普遍从早期的“表单堆叠式桌面软件”向以下模式演进：

### A. 工作流化（workflow-first）

典型特征：

- 顶部或侧边有步骤条 / 阶段导航；
- 每一步只暴露当前任务需要的参数；
- 上一步的输出成为下一步的只读输入或可追溯上下文；
- 结果可以汇总回总览页。

SeisWave 当前四步流程已经符合这一趋势，建议继续强化，而不是回退为“多标签页平铺所有功能”。

### B. 以图表和诊断信息为中心

现代科学 GUI 不再把图表放在“结果页最下面”，而是：

- 在参数输入时就**实时预览**目标谱；
- 在计算中显示**中间状态**（当前迭代误差、收敛趋势、候选波数量变化）；
- 在结果中提供**对比视图**（目标谱 vs 匹配谱、天然波 vs 人工波、单条 vs 平均包络）。

对 SeisWave 而言，图表建议始终承担三类职责：

- 预览：参数变更即看到趋势；
- 诊断：解释算法为何收敛/不收敛；
- 验证：帮助用户判断是否满足规范要求。

### C. 渐进披露（progressive disclosure）

在高复杂度参数界面里，成熟产品越来越少把所有参数一次性摊开，而是采用：

- 核心参数默认展开；
- 高级参数折叠；
- 特定模式参数按条件显隐；
- 不常改的全局偏好放入设置对话框；
- 用推荐默认值降低首用门槛。

这与 SeisWave 当前 `ParamCard` 可折叠、按地震动类型显隐的方向一致，应继续系统化。

### D. “仪表盘化”的结果解释

现代工程软件更强调“结果可信度”而不是只给原始数值：

- 成功/警告/失败状态色；
- 最大偏差、平均偏差、收敛轮数、是否满足规范阈值；
- 对异常结果给出可操作建议，例如“主周期点偏差超 20%，建议放宽筛选容差或增加候选天然波数”。

SeisWave 特别适合建立“结果摘要卡 + 规范校核卡 + 导出准备状态”三类结果卡片。

## 2.2 针对 SeisWave 的界面架构建议

建议将整个产品抽象为三层：

### 第一层：全局工作台层

- 顶部：项目标题、当前工程状态、主题切换、语言切换、帮助入口。
- 左侧：设防参数 / 规范谱上下文（如果长期存在，则作为全局上下文区）。
- 中部：当前步骤主任务区。
- 底部：状态条（计算状态、后台任务、最近告警、日志入口）。

### 第二层：步骤页面层

每一步都遵循统一骨架：

- 左：参数与过滤条件；
- 中：图表 / 表格 / 主操作区；
- 右：摘要、说明、诊断、规范提示；
- 底：主按钮与进度信息。

### 第三层：通用组件层

应该沉淀为统一组件，而不是在每个 panel 里各写一遍样式：

- `PrimaryButton`, `SecondaryButton`, `DangerButton`
- `ParameterCard`, `MetricsCard`, `DiagnosticCard`
- `PlotCard`, `TableCard`, `EmptyState`
- `StatusBadge`, `ToleranceIndicator`, `SpecCheckCard`
- `LoadingOverlay`, `ErrorBanner`, `InlineHint`

这样做的价值不只是美观，更是让验收测试对象稳定：测试可以围绕一致的 `objectName`、交互契约和状态模型构建。

## 3. PyQt5 / PySide6 主题引擎与样式系统最佳实践

> SeisWave 当前主代码实际是 `PySide6`，虽然题目写的是 PyQt5 项目调研，但对 Qt Widgets 生态的大部分结论对二者通用。

## 3.1 不建议“全靠 QSS”解决所有问题

QSS（Qt Style Sheets）非常适合做：

- 颜色、边框、圆角、内边距；
- 不同状态的视觉反馈；
- 统一按钮/输入框/组框风格；
- 为组件添加品牌层视觉一致性。

但 QSS 不擅长：

- 精细布局逻辑；
- 复杂自适应行为；
- 图表主题与业务状态联动；
- 跨平台原生风格深度整合。

最佳实践是：

- **布局和行为放 Python 代码层**；
- **视觉 token 和通用控件风格放 QSS**；
- **图表（matplotlib）主题独立维护，但与全局 token 对齐**；
- **深浅色切换不做简单字符串替换**，而是用主题对象统一生成。

SeisWave 当前 `generator_panel.py` 中对暗色模式采用替换颜色字符串的办法，只适合短期。中期建议升级为显式 token 模型。

## 3.2 推荐的主题系统结构

建议建立如下结构：

```text
seiswave/gui/styles/
  tokens.py          # 颜色、字号、间距、半径、阴影、图表色板
  theme_light.py     # 浅色主题 token
  theme_dark.py      # 深色主题 token
  qss/
    base.qss         # 通用结构样式
    widgets.qss      # 通用组件样式
    panels.qss       # 各类卡片/容器样式
    tables.qss       # 表格和 header
  mpl_theme.py       # matplotlib 风格映射
```

核心原则：

- QSS 只消费 token，不直接散落硬编码值；
- 业务代码不直接写颜色字符串；
- 图表颜色与 Widgets 主题统一；
- 成功/警告/错误色要在表单、进度条、结果卡、图表标注中一致出现。

## 3.3 Qt Widgets 工程里常被忽视但很重要的点

### A. `objectName` 与语义属性

为了测试稳定性和样式可控性，建议为关键控件统一设置：

- `objectName`：例如 `runButton`、`waveTypeCombo`、`targetSpectrumPlot`、`resultSummaryCard`
- 自定义属性：例如 `state=active|done|pending`、`severity=warning|error|success`

这既利于 QSS 选择器，也利于 `pytest-qt`、Squish 这类工具稳定定位控件。

### B. 统一间距与密度

科学软件最容易出现“控件都能用，但视觉很挤”。建议固定一套密度规范：

- 页面外边距：8/12/16 三档；
- 卡片内边距：8 或 12；
- 表单行距：6 或 8；
- 控件高度：28/32 两档；
- 标题层级：页面标题 > 卡片标题 > 字段标签 > 辅助说明。

SeisWave 当前主题里控件高度、边框、字体已有雏形，可以直接制度化。

### C. 图表主题与 Widgets 解耦但同步

因为 SeisWave 使用 `matplotlib`，建议：

- 建立统一的 plot palette；
- 在深浅色切换时同步更新背景、网格、刻度、图例；
- 对关键曲线使用固定语义色，如：目标谱=蓝、平均谱=绿、超限=橙/红、参考包络=灰；
- 避免每个 plot widget 自己决定颜色。

### D. 尽量不要在业务逻辑里临时拼样式字符串

长期看，这会让主题和逻辑耦合。推荐用：

- 主题对象生成样式；
- 通用组件承载视觉；
- 业务代码只传递状态，不直接关心颜色值。

## 4. 可访问性（Accessibility）与国际化（i18n）策略

## 4.1 科学软件也需要可访问性，不只是 Web 才需要

SeisWave 的主要用户是结构工程师，但这并不意味着可以忽略可访问性。桌面科学软件的可访问性重点通常不是“屏幕阅读器优先”，而是：

- 键盘可达；
- 高对比度可读；
- 图表不只靠颜色编码；
- 文案和状态反馈明确；
- 表格/表单焦点顺序合理；
- 错误提示可定位到具体字段。

## 4.2 对 SeisWave 最重要的 8 条可访问性建议

### 1. 为关键控件设置可访问名称和说明

对按钮、组合框、输入框、图表容器、进度条设置：

- accessible name
- accessible description
- tooltip（必要时）

尤其是动态参数区，如果某个控件只有缩写或专业代号，必须给出完整说明。

### 2. 颜色不能是唯一信号

例如“通过/警告/失败”不要只靠绿黄红显示；应同时提供：

- 图标；
- 文本标签；
- 数值阈值说明。

### 3. 焦点顺序必须按任务流走

高参数密度表单中，Tab 顺序错误会非常痛苦。建议按“上到下、左到右、先核心后高级”的顺序显式设置 tab order。

### 4. 对动态显隐控件保持稳定布局

如果切换地震动类型后大量控件突然消失/跳位，会影响理解。较好的策略：

- 只切换相关组；
- 保持卡片顺序稳定；
- 新出现的区域加标题和说明；
- 尽量不要让页面高度剧烈变化。

### 5. 表单错误要就地提示

例如：

- 阻尼比超范围；
- T1/T2/T3 为空；
- 迭代次数设置不合理；
- 隔震前后周期互相矛盾。

应在字段旁显示错误，而不只是最终弹一个 `QMessageBox`。

### 6. 图表要支持缩放、导出、重置视图

这既是生产力，也是一种可访问性增强：用户能主动调整呈现形式。

### 7. 支持系统字体放大或应用内密度切换

工程师可能在大屏、投影、Retina 屏、低视力场景下使用。建议支持：

- 标准密度 / 紧凑密度；
- 正常字号 / 放大字号。

### 8. 长任务提供取消和失败恢复

长耗时任务没有取消按钮，是桌面软件体验大坑。对科学软件尤其如此。

## 4.3 国际化（i18n）建议

SeisWave 当前明确是中文界面，但仍建议从一开始做**可翻译架构**，原因包括：

- 工程软件常出现中英混排术语；
- 部分第三方或学术合作场景需要英文界面；
- 日后导出报告、图表标题、日志文本可能需要双语。

### 建议做法

- 所有 UI 文案统一走 Qt 的翻译机制（`tr()` / `QCoreApplication.translate()`）；
- 文案不要写死在业务逻辑中；
- 单位和数值格式分离；
- 图表标题、轴标签、导出报告标题也纳入翻译资源；
- 维护术语表，例如：
  - 人工波 / Artificial Ground Motion
  - 近场脉冲 / Near-Fault Pulse-like Motion
  - 反应谱 / Response Spectrum
  - 底部剪力 / Base Shear

### 对中文科学软件尤其要注意

- 缩写首次出现要给中文全称；
- 英文缩写建议保留，例如 PGA、PGV、RSN、GMPE，但配中文说明；
- 单位规范化，例如 `s`、`g`、`cm/s`、`m/s^2`；
- 结果报告中避免同一概念多种翻译并存。

## 5. 复杂参数面板 UX 模式：适用于 SeisWave 的设计建议

SeisWave 的人工波与选波场景属于典型的“高耦合参数 + 条件分支 + 专业术语密集”问题，最适合采用下面几种 UX 模式组合。

## 5.1 模式一：主任务驱动 + 动态参数子集

以“地震动类型选择”为入口是合理的，但需要做到：

- 先选类型，再展示对应参数；
- 不同类型共享参数放在公共卡片；
- 类型专属参数放在独立卡片；
- 切换类型时保留合理默认值，并明确告知哪些参数被重置。

适用于 SeisWave 的卡片拆分建议：

- `目标谱与规范上下文`
- `基础生成参数`
- `算法控制参数`
- `地震动类型专属参数`
- `高级诊断参数`
- `结果摘要 / 可信度`

## 5.2 模式二：实时合法性校验 + 推荐默认值

复杂参数界面中，用户不怕参数多，怕的是不知道“怎么填才对”。因此建议：

- 每个关键参数提供默认值与推荐区间；
- 输入后立即校验范围；
- 对组合约束进行联动校验，例如：
  - 隔震前周期应小于隔震后周期；
  - 选波主周期点必须已定义；
  - 迭代次数过小可能无法收敛。

可视化方式建议：

- 正常：灰/蓝边框；
- 警告：橙色说明；
- 错误：红色边框 + 行内文本；
- 推荐：帮助文本说明“常用值”。

## 5.3 模式三：右侧摘要区固定，不随表单滚动而消失

SeisWave 当前右栏结果摘要方向是对的。对复杂参数任务，右侧摘要区最好承担：

- 当前模式说明；
- 关键输入摘要；
- 计算状态；
- 收敛指标；
- 规范校核结果。

这样用户在滚动长表单时不会失去上下文。

## 5.4 模式四：高级参数折叠，但要“可见其存在”

高级参数不要默认展开，但必须让用户知道“还有这部分能力”。建议：

- 折叠标题写清楚用途，如“高级迭代控制”“近场脉冲诊断参数”；
- 折叠标题旁展示简短摘要，如“当前：50 次迭代 / 容差 5%”；
- 被折叠时仍显示关键状态。

## 5.5 模式五：图表联动反馈，而不是只在点 Run 后给结果

对 SeisWave 尤其重要：

- 改规范谱参数 -> 目标谱即时刷新；
- 改选波过滤条件 -> 候选数量即时估计；
- 改关键生成参数 -> 右栏可给出预估持时/PGA/模式说明；
- 迭代中 -> 进度与误差曲线同步更新。

## 5.6 推荐的 SeisWave 参数交互原则

给 SeisWave 一句具体的设计原则：

> 左边让用户“输入”，中间让用户“看见影响”，右边让用户“理解后果”。

这比单纯“左边一堆控件，中间一张图”更适合科学软件。

## 6. 自动化验收测试框架对比

本节关注的是 GUI 验收测试，不是算法单元测试。

## 6.1 `pytest-qt`

### 优点

- Python 生态友好，易与 `pytest` 集成；
- 能驱动 Qt 事件循环，适合控件交互、信号断言、等待异步任务完成；
- 与现有 Python 单元测试体系兼容最好；
- 对 SeisWave 这种 Python + Qt Widgets 项目，进入成本最低。

### 局限

- 更偏开发者测试，不是最强的黑盒端到端录制工具；
- 对复杂跨窗口系统对话框、原生菜单、打包后应用验证能力有限；
- 做大规模视觉回归需要额外配套。

### 适配结论

**最适合 SeisWave 的基础方案。** 应作为主轴，而不是备选。

## 6.2 Qt Test / QTest

### 优点

- 官方 Qt 测试框架，事件模拟和 Qt 语义贴近；
- 对底层控件交互和事件处理很稳定。

### 局限

- 在 Python 项目里直接作为主验收方案不如 `pytest-qt` 顺手；
- 更适合库级、控件级测试，不一定适合作为完整项目测试组织层。

### 适配结论

适合做**底层 widget 交互补充**，但不建议作为 SeisWave 验收主框架。

## 6.3 Squish for Qt

### 优点

- 商业级 GUI 自动化，支持对象识别、录制回放、黑盒/灰盒方式；
- 对打包后的桌面应用测试更友好；
- 在回归测试和非开发人员可参与的场景里有优势。

### 局限

- 商业授权成本高；
- 脚本维护仍需要规范命名和稳定对象树；
- 对小团队来说投入偏重。

### 适配结论

适合 SeisWave 进入交付期、需要更强黑盒回归保障、或需要测试已打包 `.app` 时再考虑。

## 6.4 Playwright for Qt / 类浏览器式驱动思路

严格说，Playwright 原生主要是 Web 自动化。社区里存在把桌面/Qt 界面接入类似自动化模型的尝试，但成熟度、生态一致性、维护性通常不如 Qt 原生测试路线。

### 适配结论

- 如果 UI 是 Qt Widgets 原生桌面，不建议把它作为主测试方案；
- 除非未来 SeisWave 有 Web 前端或嵌入式 Web 控件占主导，否则收益有限。

## 6.5 其他可配套工具

### 截图 / 视觉回归

可考虑：

- `pytest-mpl`（更适合 matplotlib 图输出一致性）
- `Pillow` / `imagehash` / `pixelmatch` 风格工具（自建截图对比）

### 覆盖率与基准

## 7. 科学计算软件的验收测试策略

SeisWave 的验收测试不能照搬普通 CRUD 桌面软件。更合理的是三层验收模型。

## 7.1 第一层：数值正确性验收（最重要）

要验证的不是“按钮能不能点”，而是：

- 规范谱计算是否仍满足已知样例；
- 选波筛选是否仍按规范约束运行；
- 反应谱偏差是否在容差内；
- 生成的人工波是否达到目标匹配指标；
- 组合输出后的平均/包络是否满足规范门槛。

### 建议做法

建立一组**黄金数据集（golden cases）**：

- Case A：常规抗震谱 + 常规天然波筛选
- Case B：隔震谱 + 双周期校核
- Case C：人工波时域法匹配
- Case D：人工波频域法匹配
- Case E：5+2 组合输出
- Case F：2+1 组合输出

每个 case 固定：

- 输入参数；
- 参考输出摘要；
- 容差定义（例如相对误差、最大偏差、平均偏差、收敛轮次上限）。

这是 SeisWave 最有价值的验收资产。

## 7.2 第二层：GUI 交互验收

要覆盖的不是所有像素，而是关键业务流：

- 用户是否能完成一步到下一步；
- 参数切换后界面状态是否正确；
- 长任务期间 GUI 是否仍响应；
- 错误输入是否正确提示；
- 结果摘要、图表、导出按钮是否进入正确状态。

### 对 SeisWave 建议覆盖的关键路径

1. 设置规范谱参数并看到目标谱更新
2. 切换到选波页，运行筛选并得到候选结果
3. 切换到生成页，选择不同地震动类型，验证动态参数显隐
4. 运行人工波生成，等待线程完成，验证结果摘要与图表更新
5. 进入组合页，完成组合并导出
6. 输入非法参数，验证就地错误或禁用运行按钮

## 7.3 第三层：性能与稳定性验收

需求文档已经给出性能目标，因此应把它们转化为自动化基准：

- 701 条天然波批量加载 <= 10 秒
- 701 条波反应谱批量计算 <= 60 秒
- 单条人工波 50 次迭代 <= 10 秒（Fortran 加速后）
- 长计算期间主线程不冻结

### 推荐做法

- 在 CI 中只跑**小样本性能 smoke**，避免波动太大；
- 在本地或 nightly 跑**完整基准**；
- 把性能门槛设置为“告警”或“趋势监控”，不要把所有性能测试都设成硬阻塞；
- GUI 响应性可通过事件循环心跳、进度信号频率、超时阈值来断言。

## 8. CI/CD 中 GUI 测试的 headless 执行方案

## 8.1 最现实的方案：Linux + Xvfb + pytest-qt

这是多数 Qt/PySide CI 的常见组合，优点：

- 成熟稳定；
- 不依赖真实显示器；
- 与 `pytest-qt` 兼容较好；
- 成本低，适合 GitHub Actions / GitLab CI / 自建 runner。

典型做法：

- 安装 Qt/PySide6 依赖；
- 使用 `xvfb-run -a pytest ...` 运行 GUI 测试；
- 对需要纯图像导出的测试，matplotlib 使用 `Agg`；
- 对需要真实 QWidget 渲染的截图测试，保留 Qt 图形环境。

## 8.2 `QT_QPA_PLATFORM=offscreen`

优点：

- 启动轻；
- 某些控件级测试可直接跑。

风险：

- 某些绘图、尺寸计算、原生行为和焦点交互与真实显示环境存在差异；
- 不适合作为唯一的 GUI 验收环境。

### 结论

适合作为补充，不适合单独承担全部验收责任。

## 8.3 macOS Runner

因为 SeisWave 的目标平台强调 macOS 原生支持，建议：

- 平时 CI 主要在 Linux headless 跑快速回归；
- 每日或发布前在 macOS runner 上跑一轮 smoke / 打包后启动测试；
- 对 `.app` 打包、字体渲染、Retina 缩放、系统菜单行为的验证，macOS runner 更有价值。

## 8.4 推荐的 CI 分层

### PR 级

- 单元测试
- 黄金数值样例测试
- 少量 `pytest-qt` GUI smoke
- 快速截图回归（只测少量关键图）

### Nightly / Release 级

- 完整 GUI 回归
- 更大样本的性能基准
- macOS 打包启动 smoke
- 导出报告和文件格式回归

## 9. 截图回归测试（Visual Regression）可行性

## 9.1 可行，但要控制范围

对 SeisWave 来说，截图回归是**可行但不应过量依赖**的。原因：

- 图表和表单布局对业务体验很重要；
- 但跨平台字体、抗锯齿、DPI、主题差异会造成噪声；
- 如果对整页截图做严格逐像素比较，维护成本会很高。

## 9.2 适合截图回归的对象

建议只对以下高价值区域做视觉基线：

- 步骤条状态变化
- 关键参数卡片布局
- 生成页三栏布局完整性
- 结果摘要卡状态色与字段位置
- 典型反应谱图的基本外观
- 导出报告中的关键图表

## 9.3 不适合截图回归强绑定的对象

- 高频变化的动画/进度瞬态
- 含随机数据但未固定种子的图表
- 字体渲染强依赖平台的整页截图
- 受系统主题影响明显的原生控件细节

## 9.4 实施建议

- 固定字体、DPI、随机种子、matplotlib 后端；
- 关键图表尽量在相同数据和相同尺寸下渲染；
- 使用阈值比对，而不是绝对逐像素一致；
- 将截图回归作为“辅助警报”，而不是唯一阻塞条件；
- 图表更适合做“结构性断言 + 少量视觉基线”组合。

### 结论

**SeisWave 可以做 visual regression，但应聚焦于少量关键视图，而不是全面铺开。**

## 11. 对 SeisWave 的具体推荐路线

## 11.1 UI 设计推荐

### 短期（现在就做）

- 保留现有四步向导主结构；
- 统一参数卡片、结果卡片、状态卡片命名和样式；

### 中期

- 提炼正式 design tokens；
- 建立 light/dark 主题对象，而不是字符串替换；
- 增加语言切换和术语表管理；
- 把结果解释做成“规范校核摘要 + 诊断建议”组件。

### 长期

- 针对不同工作模式提供专家/标准视图；
- 做工程模板、最近项目、结果对比工作台；
- 加强报告导出的一致视觉语言。

## 11.2 测试体系推荐

### 最推荐的实际路线

对于 SeisWave，这三步最现实：

1. **立刻采用方案 A**：先把黄金数值样例 + `pytest-qt` 关键流程建起来。
2. **一旦 GUI 结构趋稳，升级到方案 B**：加入少量截图回归与 macOS smoke。
3. **只有在交付要求明显提高时再考虑方案 C**：尤其是商业工具和打包后黑盒回归。

## 11.3 为什么不建议一开始就上重型 GUI 黑盒方案

因为 SeisWave 当前最大风险不是“按钮点不到”，而是：

- 核心数值结果回归；
- 参数联动逻辑复杂；
- 主题和布局可能频繁变化；
- Fortran/Python 计算链的性能与稳定性。

在这个阶段，**黄金样例 + 关键流程自动化**的 ROI 最高。

## 13. 结论

对 SeisWave 这类科学计算桌面工具，好的 UI 不是“像消费级 App 一样花哨”，而是让工程师在高参数密度和高数值责任下仍然**看得懂、改得准、信得过**。当前 SeisWave 的向导式工作流、卡片化参数区、三栏生成页已经是正确方向，下一步应该把这些局部设计提升为完整的设计系统。

- **用黄金样例守住数值正确性**；
- **用 `pytest-qt` 守住关键交互流**；
- **用少量截图回归守住布局和图表质量**；
- **用 CI headless 和 macOS smoke 守住持续集成可落地性**。

如果只能给一个最务实建议：

> 先做“方案 A + 少量方案 B 元素”，这是当前 SeisWave 投入产出比最高的路径。
